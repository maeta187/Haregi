# テストルール(Vitest・TDD)

## TDD(必須)

フロントエンド・バックエンドともに **TDD(テスト駆動開発)** で実装する。実装前に失敗するテストを書き(Red)→ 実装して通す(Green)→ 必要ならリファクタリング(Refactor)、のサイクルを各層・各コンポーネントで回す。テストを後追いで書かない。

必須のテスト対象:

- `packages/schema`: Zod バリデーションスキーマ(境界値)/ 地域マスタ(コードの一意性・形式)/ 日付(JST)・気温整形ユーティリティ(**`TZ=UTC` でも JST 判定が正しいこと**)
- `apps/api`
  - `domain`: 気象庁 JSON → `Forecast` 型への正規化(短期・週間の統合、欠損 `""`、奄美・十勝の親区分解決)/ コーデのビジネスルール(items 上限)/ 気温スナップショットの決定(予報範囲外は null)
  - `application`: ユースケース。infrastructure の `Result` → 型付きアプリケーションエラーへの変換 / **気温スナップショットが指定 `snapshotId`(表示していた予報の世代)から解決されること** / **`snapshotId` なしの更新で既存の気温・由来が維持されること**(決定事項 #31)
  - `infrastructure`: 地域コード単位のキャッシュ動作(**世代の引き当て・TTL 切れ後の last-known-good・同時リクエストの束ね**)/ 一括 upsert のトランザクション(部分失敗時に全件ロールバック)/ **楽観ロック**(下記)
  - `presentation`: 認証ミドルウェアの 401 応答 / エラー → HTTP ステータス(400 / 409 / 502 等)のマッピング
  - **楽観ロック(決定事項 #32)**: 値の不一致だけを見るテストでは、省略による迂回も真の同時更新も検出できない。次の4つを必ず書く
    - `updatedAt` が DB と**不一致**の item を含む保存が 409 になること
    - 既存レコードに対して `updatedAt` を**省略**した保存が 409 になること(fail-closed。任意扱いのままだと無言の上書きが通る)
    - **同一レコードへの並行保存**で、後着の1本が 409 になること(`WHERE ... AND updated_at = ?` の条件付き書き込みで更新件数0を競合として扱えているか。事前照合と書き込みを分けた実装では両方通過してしまう)
    - **空入力による削除分岐**でも `updatedAt` が照合され、不一致・省略なら削除されずに 409 になること
    - **保存が成功した行の `updatedAt` が前進していること**。保存レスポンスで返った新しい値では続けて更新でき、**保存前の古い値では直ちに 409** になること(前進させない実装では旧トークンが有効なまま残り、同じ値で何度でも更新できてしまう)
    - いずれの 409 でも**同一リクエスト内の他 item が一切適用されない**こと(全件ロールバック)
  - **認可(所有権)**: RLS を持たない構成のため、**この保証はテストが担う**(`api-design.md`「認可の実施場所」)。コーデ機能の各操作について、**他ユーザーのレコードを取得・更新・削除できないこと**を必ず1ケースずつ書く(削除は独立エンドポイントだけでなく、**`PUT` の空入力による削除分岐**も対象)
    - `GET /api/coordinates` に他ユーザーのレコードが混ざらないこと
    - `PUT /api/coordinates` で他ユーザーの同一日付レコードを書き換えられないこと(自分の新規レコードが作られる)
    - `PUT /api/coordinates` の**空入力による削除分岐**(3項目が trim 後すべて空 → その日付のレコードを削除。`validation.md`)で、**他ユーザーだけが対象日付のレコードを持つ状態でも、そのレコードが残ること**。削除分岐を日付だけで引く実装(`WHERE date = ?`)を検出できる唯一のケースであり、更新側のテストでは代替できない。併せて、削除分岐を含む一括リクエストの全 item が `userId` 条件と同一トランザクションを維持することも検証する
    - `DELETE /api/coordinates/:date` で他ユーザーのレコードが消えないこと(応答は 404 / 該当0件で、403 との出し分けをしない)**— 削除機能(Should)着手時**
    - 写真(Should 着手時): 他ユーザーのプレフィックスを持つ `imageKey` の確定が拒否されること
  - **空入力 item の分岐**(`api-design.md`「空入力 item の扱い」): 削除・no-op・409 の出し分けを固定する
    - 自分のレコードが**存在しない**空行は **no-op**(200)。`updatedAt` の有無を問わず 409 にしない
    - **他ユーザーだけが**同日のレコードを持つ場合も no-op であり、他ユーザーのレコードは残ること
    - 自分のレコードがあり `updatedAt` が一致する空行は削除されること
    - **未入力の日を含む一括送信**(部分入力した週)が全件成功すること。ペルソナの常態(週初めにまとめて入力し未入力の行が残る)であり、ここで 409 が出るとバッチ全体が失敗する
- `apps/web`: `@testing-library/react` + `@testing-library/jest-dom` によるコンポーネントテスト。`components/` は props のみの純粋コンポーネントとして、`hooks/` は `features/*/api/` をモックしてテストする(決定事項 #28)。必須ケース: フォームバリデーション表示 / 保護ルートの未認証リダイレクト / 予報取得失敗時のエラー表示+再試行 / **予報が取れなくてもコーデを保存できること** / 出典表記の常時表示

方針:

- **コンポーネントテストはスコープ内。E2E(Playwright 等)は今回スコープ外**。E2E の追加を提案しない
- lint / format / typecheck / test は手動実行(`pnpm lint` / `pnpm format` / `pnpm typecheck` / `pnpm test`)。Husky 等の Git フックを追加しない
- シードは Better Auth の `auth.api.signUpEmail` 経由で作成する(ハッシュ形式を揃えるため DB へ直接 INSERT しない)。テストユーザー: `admin@example.com` / `password123` / 地域 `130000`

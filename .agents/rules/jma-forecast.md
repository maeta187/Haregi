# 気象庁 API 取り扱いルール

エンドポイント: `https://www.jma.go.jp/bosai/forecast/data/forecast/{forecastCode}.json`(非公式 API)

## 構造仕様(全58区分の実レスポンスで検証済み — この前提を崩さない)

- レスポンスは `[短期予報, 週間予報]` の**2要素配列**。天気・降水確率は一次細分区域(`weatherArea` / `weeklyArea`)単位、気温はアメダス地点(`tempStation`)単位とキーが異なる
- **週間予報は翌日始まり**。当日の気温は短期パートから補完する
- 空文字 `""` の欠損値が入るため、欠損処理を必須とする
- **奄美(460040)・十勝(014030)は自分の JSON を持たない(404)**。地域マスタの `forecastCode`(親区分)で取得する。区分コードから URL を直接組み立てない
- 週間の天気・降水確率は大半の区分で広域統合される。解決はマスタの `weeklyArea` に従う(福島のみ中間区域 070100)
- 取得・整形は `apps/api` の `features/forecast/` 内に隔離する(**正規化ロジックは `domain` の純粋関数、取得・キャッシュは `infrastructure`**。決定事項 #26)。共通の `Forecast` 型へ正規化してから他層・他 feature に渡し、気象庁 JSON の生の形を外に出さない
- 天気アイコン(天気コードのマッピング)・降水確率は Should。Must の段階では週間の最高/最低気温の表示を優先する

## キャッシュ・障害時

- 地域コード単位でサーバー側キャッシュ(30〜60分・インメモリ)。ユーザーごとに気象庁へ直接リクエストしない
- 取得失敗時は 502 を返す。フロントは予報部にエラーメッセージ+再試行ボタンを表示し、TanStack Query の stale データがあれば表示する
- **予報が取れなくてもコーデ入力・保存は必ず継続できる**こと(気温スナップショットは null)
- 気温スナップショットは**リクエストの `snapshotId`(画面に表示していた予報の世代)**が指す世代から解決する。登録地域固定にせず(決定事項 #29)、保存時に予報を引き直さない(決定事項 #30)
- **世代(`snapshotId`)は PostgreSQL の `forecast_snapshot` テーブルに永続化する**(決定事項 #34)。取得ごとに1行を書き、`payload` には**正規化済みの `Forecast`** を入れる(気象庁の生 JSON を DB に残さない)。**保持は24時間**。**失効の判定は引き当てクエリの条件で行う** — `WHERE snapshot_id = ? AND created_at > now() - interval '24 hours'` とし、期限切れの行が残っていても引き当てを失敗させる。行の掃除は予報取得時に走らせるが、**容量管理のためであって失効判定の根拠にしない**(掃除に頼ると、24時間経過後に予報 `GET` を挟まず古い画面から直接 `PUT` した場合に期限切れの行が引き当たってしまう)
- **世代をインメモリキャッシュに置かない**。プロセス再起動(デプロイ・クラッシュ・ローリング更新)や複数インスタンスでは引き当てられず、画面に出ていた気温と保存値が黙って食い違う。「Node 常駐プロセス」は再起動や水平スケールを防ぐ保証ではない
- **インメモリキャッシュの役割は気象庁への発信抑制に限る**(TTL 30〜60分)。再取得に失敗しても最後に成功した予報を破棄せず `status: 'stale'` として返す(last-known-good)。同一地域への並行取得は1本の fetch に束ねる
- **stale を返すときも新しい `forecast_snapshot` 行を発行し、有効な `snapshotId` を返す**(`status: 'stale'`、`fetchedAt` は最後に成功した取得時刻)。**`GET /api/forecast` が 200 を返す限り、その `snapshotId` は必ず引き当て可能**という不変条件を保つ。これを破ると、気象庁の障害が24時間を超えた時点で「stale 表示のまま元の世代は期限切れ」となり、保存が 409 →再取得 →同じ stale 表示 →また 409 のループになって、**「予報が取れなくてもコーデ入力・保存は継続できる」(Must)が満たせなくなる**
- **`snapshotId` が送られたのに解決できない場合(保持期間超過・掃除済み)は 409** を返し、予報の再取得と再送を求める(決定事項 #35)。**送られていない場合**は従来どおり既存の気温・由来を維持する(決定事項 #31)。両者を混同しない
- インメモリキャッシュは Node 常駐プロセス前提。サーバーレスデプロイを検討する場合は再設計が必要(決定事項 #23)。ただし世代の引き当ては DB に移したため、保存時の気温解決はプロセス構成に依存しない

## 法的要件

- 予報は**改変せずそのまま表示**する。独自予報・独自の気象予測を生成しない(気象業務法)
- 「出典: 気象庁ホームページ」を予報表示部またはフッターに**常時表示**する(政府標準利用規約)
- AI 提案(将来)でも気象庁の予報値は入力にそのまま使い、改変しない

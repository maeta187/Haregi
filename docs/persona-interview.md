## ラウンド1: 前提(誰のため・何の課題・いつ使う)

### Q1. このアプリは第一に「誰のため」に作っていますか?

| 選択肢 | 補足 |
| --- | --- |
| 自分自身がメインユーザー | 自分の困りごとを解決する個人開発。ペルソナは「自分」を言語化する形になる |
| 身近な特定の誰か | 家族・パートナー・友人など。要望を直接聞ける強みがある |
| **不特定多数への公開を目指す** ✅ | 一般ユーザー向けのサービスとして育てたい。ペルソナは市場セグメントとして立てる必要がある |
| 自分用+将来的に公開 | まず自分が使い、手応えがあれば公開 |

**回答: 不特定多数への公開を目指す**

### Q2. 服装の記録で解決したい困りごとは何ですか?(複数選択可)

| 選択肢 | 補足 |
| --- | --- |
| 毎朝の服選びに迷う | 何を着るか決めるのに時間がかかる。気温を見ても服に変換できない |
| 過去に何を着たか忘れる | 去年の同じ時期・同じ気温の日に何を着ていたか思い出せない |
| **寒すぎ/暑すぎの失敗** ✅ | 予報の気温を見誤って一日中不快な思いをする。体感とのズレを埋めたい |
| 同じ服ばかり着てしまう | 手持ちの服を活かせていない。記録して偏りを可視化したい |

**回答: 寒すぎ/暑すぎの失敗**(単一選択)

### Q3. 主にいつ使う想定ですか?(複数選択可)

| 選択肢 | 補足 |
| --- | --- |
| 朝、出かける前 | 当日の予報を見てその場で服を決めて記録する。速度が最重要になる |
| **夜、翌日の準備** ✅ | 翌日の予報を見て服を決めておく。週間予報の価値が高まる |
| 帰宅後に記録 | その日着たものを事後的に記録する。記録アプリとしての性格が強くなる |
| 週末にまとめて振り返る | 履歴一覧を眺めて傾向を見る |

**回答: 夜、翌日の準備 / 1週間分まとめて**

> **この回答が最大の転換点**。「まとめて」が振り返りではなく**入力**を指していたため、記録アプリではなく計画ツールだと判明した。

### Q4. 想定ユーザーのファッションへの関わり方は?

| 選択肢 | 補足 |
| --- | --- |
| 中: 失敗したくない | おしゃれが目的ではないが、季節外れ・不快な格好は避けたい実用重視の層 |
| **高: コーデを楽しむ** ✅ | 服が好きで、着回しや記録そのものを楽しむ。写真・履歴機能の価値が高い |
| 低: 寒暖の失敗回避だけ | 服選びはむしろ面倒。「今日は何を着ればいいか」の答えだけ欲しい層 |

**回答: 高: コーデを楽しむ**

### ラウンド1 時点の解釈

**「おしゃれは好きなのに、気温の読み違いでその日の服装を失敗する」層**。実用一辺倒(関与度・低)でも、着回し記録が目的(課題=同じ服ばかり)でもない中間に位置する。

特筆点として、「1週間分まとめて」が既存設計の `PUT /api/coordinates`(**items 最大7件**の一括 upsert)および週間予報中心の `/forecast` 画面と偶然整合していることを確認した。

## ラウンド2: 具体像(年齢・デバイス・生活パターン)

### Q5. 想定ユーザーの中心年齢層は?

| 選択肢 | 補足 |
| --- | --- |
| **20代後半〜30代前半** ✅ | 社会人数年目。服にお金をかけられ、通勤・休日で服を使い分ける層 |
| 20代前半(学生・新社会人) | トレンド感度が高く SNS 親和性も高いが、手持ちの服は多くない |
| 30代後半〜40代 | 服の資産が蓄積されており、「去年何を着たか」の振り返り価値が最も高まる層 |
| 幅広く(年齢で絞らない) | 年齢ではなく行動(週単位で服を計画する)で定義する |

**回答: 20代後半〜30代前半**

### Q6. 主な利用デバイスは?

| 選択肢 | 補足 |
| --- | --- |
| **スマホ中心** ✅ | クローゼットの前やベッドで片手操作。モバイル優先の UI 設計が必須になる |
| スマホ中心だが PC も使う | 日々の記録はスマホ、週末のまとめ入力や振り返りは PC |
| PC 中心 | デスクで週間予報を見ながらまとめて入力する。一覧性を優先できる |

**回答: スマホ中心**

### Q7. そのユーザーが服を選ぶ場面の頻度は?

| 選択肢 | 補足 |
| --- | --- |
| **毎日出社・通学する** ✅ | 平日毎日服を選ぶ必要があり、週単位の計画が最も効く |
| ハイブリッド(週数回出社) | 出社日だけ服を考える。記録が飛び飛びになる前提で設計が必要 |
| 在宅中心・外出時のみ | 外出する日だけが対象。記録の連続性よりイベント単位の価値が強い |

**回答: 毎日出社・通学する**

### Q8. 「1週間分まとめて」使う一番の動機は?

| 選択肢 | 補足 |
| --- | --- |
| **週間予報を見て先に計画したい** ✅ | 先にコーデを決めておき、平日はそれに従う。記録より「計画ツール」の性格が強まる |
| 平日の朝の時間を削りたい | 毎朝迷うコストを週末に前倒しする。時短が主目的 |
| 記録をまとめてつけたい | 日々の入力は面倒なので、週末にまとめて実績を入れる。事後記録型 |
| 服の重複を避けたい | 1週間を一覧して同じ服が並ばないよう調整する。一覧性が命 |

**回答: 週間予報を見て先に計画したい**

### ラウンド2 時点の解釈

**「毎日出社する20代後半〜30代前半。おしゃれは好きだが、日曜の夜にスマホで週間予報を見て1週間分のコーデを先に決めておきたい。気温を読み違えて寒い/暑い思いをするのが嫌」**

記録アプリというより**週次のコーデ計画ツール**であることが確定した。同時に、現在の仕様が答えを持っていない論点が2つ浮上した:

1. **計画と実績のズレ** — `(userId, date)` で1日1レコードのため、当日に別の服を着た場合の扱いが未定義。さらに気温スナップショットは保存時の予報から引くため、日曜に入力した金曜分は「4日前の予報値」が記録される
2. **スマホでの一括入力負荷** — 7日 × 3項目 = 21入力欄をスマホで埋める UI が `specification.md` に未記述

## ラウンド3: 仕上げ(構成・リスク・優先度)

### Q9. ペルソナは何体立てますか?

| 選択肢 | 補足 |
| --- | --- |
| メイン1体に絞る | 迷ったら常にこの人で判断する。基準がぶれず、個人開発の規模にも合う |
| メイン + サブ1体 | サブに「関与度中の実用層」を置き、Must 機能が幅を持てるか検証する |
| **メイン + サブ2体** ✅ | 幅広く押さえられるが、全員を満たそうとして機能が膨らむリスクがある |

**回答: メイン + サブ2体**

### Q10. このユーザーが使わなくなるとしたら、原因は?(複数選択可)

| 選択肢 | 補足 |
| --- | --- |
| **入力が面倒で続かない** ✅ | 3項目×7日をスマホで打つ負荷。入力補助(前回コピー等)の優先度が上がる |
| 計画と実績がズレる | 先に決めても当日別の服を着る。計画/実績を区別するか上書きするかの設計判断が必要になる |
| **予報が外れる** ✅ | 週間予報の精度は低い。先の日ほど信頼度が下がることを UI で伝える必要が出る |
| 振り返る価値が出るまで長い | データが数ヶ月貯まるまで得がない。初期体験で何を返すかが課題になる |

**回答: 予報が外れる / 入力が面倒で続かない**

> 選ばれなかった「計画と実績がズレる」は、離脱要因としては低く見積もられたものの、データモデル上の論点としては残るため未決論点①として記録した。

### Q11. コーデ写真のアップロード(現在 Should)は、このペルソナにとって?

| 選択肢 | 補足 |
| --- | --- |
| あると嬉しい程度 | テキスト3項目で一応成立する。Should のまま維持 |
| 必須級 | 「コーデを楽しむ」層はテキストだけでは満足しない。Must への格上げを検討する |
| **初回は不要** ✅ | むしろ入力負荷になる。優先度を下げる(Could 相当) |

**回答: 初回は不要**

> 関与度「高」の層でありながら写真を不要と判断した点が重要。**Q10 の「入力が面倒で続かない」への直接的な対応**として、入力負荷の削減が写真の魅力より優先された。

### Q12. まとめたペルソナはどこに記載しますか?

| 選択肢 | 補足 |
| --- | --- |
| specification.md に新節を追加 | §1 アプリ概要の直後に「§1.x 想定ユーザー」を新設。機能要件と同じファイルで参照される |
| **docs/persona.md として独立** ✅ | 将来インタビュー結果やサブペルソナを厚く書ける。specification.md からはリンク |

**回答: docs/persona.md として独立**

## インタビューで決めなかったこと

以下はインタビューでは問わず、**回答から論理的に導出した**もの。判断の性質が異なるため区別して記録する。

- **サブペルソナ2体の中身**(当日型「ナギ」・振り返り型「セイ」)。Q9 で体数のみ決め、誰を置くかは「メインが未来(計画)を担うので、サブは現在(当日)と過去(振り返り)を担わせる」という時間軸の分担から構成した
- **3ペルソナとも性別を特定しない**方針。インタビューで性別を問わなかったため、勝手に補完せず「特定しない」と明記し、アプリ側もジェンダーを前提としない設計を維持することにした
- **非ターゲット**([persona.md](./persona.md) §6)。Q1 の「不特定多数への公開」を受け、狙わない層を明示しないと機能が発散するため追加した

# Haregi(ハレギ)ペルソナ定義

Haregi の**想定ユーザー**。「**誰のために作るか**」を定義する。何を作るか(機能要件)は [specification.md](./specification.md)、どう作るか(技術設計)は [architecture.md](./architecture.md) を参照。

- 作成日: 2026-08-01(インタビュー形式で決定)
- ステータス: 確定(§5 の未決論点を除く)
- 使い方: 機能の追加・優先度・UI を迷ったときに**メインペルソナ(§2)で判断する**。サブペルソナ(§3)は「Must 機能が狭くなりすぎていないか」を検算するためのもので、サブのために機能を足す判断はしない

---

## 1. 前提(インタビュー結果)

| 論点 | 決定 |
| --- | --- |
| 誰のために作るか | **不特定多数への公開**を目指す(自分用ツールではない) |
| 解決する困りごと | **気温の読み違いによる「寒すぎ/暑すぎ」の失敗** |
| 主な利用場面 | **夜、翌日の準備** + **1週間分をまとめて** |
| ファッションへの関与度 | **高い**(コーデを楽しむ層) |
| 中心年齢層 | **20代後半〜30代前半** |
| 主なデバイス | **スマホ中心** |
| 生活パターン | **毎日出社・通学**する |
| まとめて使う動機 | **週間予報を見て先に計画したい** |
| 継続の壁 | ①**予報が外れる** ②**入力が面倒で続かない** |
| コーデ写真の位置づけ | **初回は不要**(入力負荷になる) |
| ペルソナ構成 | メイン1体 + サブ2体 |

**この結果から導かれる本質**: Haregi は「着たものを記録するアプリ」ではなく、**週間予報を根拠に1週間分の服装を先に決めておく計画ツール**であり、記録は計画の副産物として貯まる。この順序を取り違えると UI の優先順位を誤る。

**性別は特定しない**。3ペルソナとも性別を定義せず、アプリもアウター/トップス/ボトムスの自由記述のみでジェンダーを前提としない設計を維持する。

## 2. メインペルソナ:「日曜の夜に1週間を決める人」

> **ハル / 28歳 / 都内在住・IT 企業勤務(毎日出社)**

### 基本属性

| 項目 | 内容 |
| --- | --- |
| 年齢 | 28歳(コア: 20代後半〜30代前半) |
| 居住・勤務 | 東京都在住。平日は毎日出社し、片道40分の電車通勤 |
| ファッション関与度 | **高い**。服は好きで一定の予算をかけ、着るものを自分で選びたい。ただし「毎日ゼロから考える」のは負担 |
| デバイス | **スマホ中心**。PC は仕事用で、アプリはほぼスマホから開く |
| リテラシー | 一般的なアプリは問題なく使う。専門用語は避けたい |

### 困りごと(なぜ Haregi が必要か)

- 朝は時間がなく、**その場で気温を見ても「何を着るか」に変換できない**。結局いつもの服になる
- 「今日は暖かい」と思って薄着で出たら、**夕方に冷えて一日不快**。あるいは着込みすぎてオフィスで暑い。**この失敗が一番のストレス**
- 通勤中に上着を脱げない・持ち歩きたくないため、**朝の判断ミスが夜まで取り返せない**
- おしゃれは好きなので、**気温の読み違いでコーデが台無しになるのが特に悔しい**(実用層とは動機が違う)

### 使い方(典型シナリオ)

1. **日曜の夜**、ベッドでスマホを開き `/forecast` で東京都の週間予報(最高/最低気温)を見る
2. 「火曜は最高18℃・最低9℃で寒暖差が大きい」と気づき、**火曜だけ薄手のアウターを追加**する形で1週間分のコーデを入力する
3. 平日は基本的に計画どおりに着る。**朝はアプリを開かないこともある**
4. 木曜あたりで「金曜の予報が変わった」と気づき、**その日だけ修正**する

### このペルソナが要求すること

| 要求 | 現在の仕様との関係 |
| --- | --- |
| 週間気温予報(最高/最低)を1画面で見渡せる | `specification.md` §2.2 Must。**充足** |
| 1週間分をまとめて入力・保存できる | `architecture.md` §5 `PUT /api/coordinates`(items 最大7件の一括 upsert)。**充足** |
| 保存済みの計画を後から修正できる | `specification.md` §2.3「保存済みコーデの表示・編集」Must。**充足** |
| スマホで7日 × 3項目を無理なく入力できる | **未定義**(§5-③) |
| 予報が外れうることが分かる | **未定義**(§5-④) |

### このペルソナが要求しないこと

- コーデ写真(§1 のとおり初回は不要。むしろ入力負荷)
- 手持ちの服の在庫管理・タンス機能
- SNS 共有・他人のコーデ閲覧
- 当日の詳細な天気(雨雲レーダー等)。**気温が主役**であり、天気アイコン・降水確率は Should のままでよい

## 3. サブペルソナ(検算用)

メインが「未来(計画)」を担うのに対し、サブは「現在(当日)」と「過去(振り返り)」を担う。**3体で同じアプリの時間軸を分担している**構造になっている。

### サブ1:「朝、出る前に確認する人」— 当日型

> **ナギ / 26歳 / 毎日出社 / ファッション関与度は中**

- 計画はしない。**朝、家を出る前に今日の気温だけ確認して服を決める**
- 動機は「失敗したくない」であり、おしゃれを楽しむためではない
- 記録は続かない前提。**入力しない日があってもアプリが壊れない**ことが条件
- **検算の役割**: `/forecast` が「1週間の一覧」に最適化されすぎて、**当日の情報が埋もれていないか**を確認する。当日分が最初に目に入り、1日だけの入力でも成立すること

### サブ2:「去年の今頃を思い出したい人」— 振り返り型

> **セイ / 35歳 / ハイブリッド勤務 / ファッション関与度は高**

- 服の資産が蓄積されており、**「去年の同じくらいの気温の日に何を着たか」**を参照したい
- Haregi を数ヶ月〜1年使い続けた**後期のユーザー像**でもある(メインペルソナの1年後の姿)
- **検算の役割**: 気温スナップショット(`maxTemperature` / `minTemperature`)を Must フェーズで実装する判断([architecture.md](./architecture.md) §4)の根拠。**このデータは後から復元できない**ため、初回リリースから貯める必要がある。`/history`(Should)と「似た気温の日に何を着たか」(Could)の受け皿

## 4. 継続リスクと対応方針

インタビューで挙がった2つの離脱要因。いずれも**初回リリースの設計で手当てが必要**。

### リスク①: 予報が外れる

週間予報は先の日ほど精度が落ちる。**計画ツールとして予報を根拠にする以上、外れは構造的に避けられない**。

- 気象庁の予報を改変せず表示する原則([specification.md](./specification.md) §5)は維持する。**独自補正は気象業務法上も行わない**
- 対応は「予報を当てる」ではなく「**外れうることを伝え、直前の修正を容易にする**」方向に倒す(§5-④)

### リスク②: 入力が面倒で続かない

7日 × 3項目 = **21入力欄をスマホで埋める**のは、現在の仕様のままでは現実的でない。

- 全項目は任意入力([specification.md](./specification.md) §4)であり、**空欄のまま保存できる**ことを UI でも明確にする
- 入力補助(前日・前回のコピー、よく使う組み合わせの再利用)は有力だが**現在の仕様に記述がない**(§5-③)
- **写真アップロードを初回スコープから外す**判断はこのリスクへの直接的な対応にあたる(§5-⑤)

## 5. 未決の論点(要判断)

ペルソナ確定により顕在化した、**現在の仕様が答えを持っていない**論点。

### ① 計画と実績のズレ

現在のデータモデルは `(userId, date)` で**1日1レコード**([architecture.md](./architecture.md) §4)。「先に計画する」使い方では、**当日に別の服を着た場合の扱いが未定義**。選択肢は (a) 上書きして実績だけを残す (b) 計画と実績を区別して両方持つ (c) 区別せず「計画=実績」とみなす。**(c) が最もシンプルだが、サブ2 の振り返り価値は「実際に着たもの」に依存する**ため、履歴機能(Should)の設計時に再判断が必要。

### ② 気温スナップショットの取得タイミング

気温スナップショットは**保存時**の予報から引く仕様([architecture.md](./architecture.md) 決定事項 #29)。日曜に入力した金曜分には「**4日前時点の予報値**」が記録される。振り返り(サブ2)で本当に欲しいのは**実際の気温**に近い値であり、計画時の予報値とは乖離しうる。当日に近いタイミングで再解決するか、計画時の値のまま許容するかは未決。

### ③ スマホでの週間一括入力 UI

7日分の入力をスマホでどう見せるか(日ごとのカルーセル / 縦スクロールの7日リスト / アコーディオン)は `specification.md` に記述がない。**メインペルソナの中核体験がここに集中している**ため、`/forecast` の実装(実装プラン フェーズ6b)前に決める必要がある。入力補助の有無もここに含む。

### ④ 予報の確度表示

「先の日ほど予報が外れやすい」ことをどう伝えるか。**気象庁データの改変にあたらない範囲**(例: 日付が先であることの視覚的表現、更新時刻の明示)に限る。

### ⑤ コーデ写真の優先度

インタビューでは「**初回は不要**」。現在の `specification.md` §2.3 では **Should**。Could への引き下げが妥当だが、優先度の変更は仕様書側の判断のため保留。引き下げる場合、[architecture.md](./architecture.md) §8(画像ストレージ)と決定事項 #17(S3 互換ストレージ)の着手時期も後ろ倒しになる。

## 6. 非ターゲット(明示的に狙わない層)

- **服装に関心がなく、寒暖の失敗すら気にしない層**。Haregi の入力コストに見合う動機を持たない
- **日本国外の利用者**。気象庁の府県予報区(全58区分)に依存しており、UI・エラーメッセージも日本語のみ([specification.md](./specification.md) §2.2)
- **屋外作業者・アウトドア用途**。求められる精度・項目(防水性、風速、体感温度)が異なり、気温中心の設計と合わない
- **ファミリー利用**(子どもの服装管理)。1アカウント1人・`(userId, date)` 一意のデータモデルと衝突する
- **ワードローブ管理を求める層**。手持ちの服の登録・在庫管理は Haregi のスコープ外

# Haregi(ハレギ)ターゲットユーザー(ペルソナ)

Haregi を**誰のために作るか**を定義する。機能の優先順位・UI・スコープ判断で迷ったときは、この人物を基準に決める。要件(何を作るか)は [specification.md](./specification.md)、技術設計(どう作るか)は [architecture.md](./architecture.md) を参照。

- 作成日: 2026-08-01(インタビュー形式で決定。specification.md §1.1 から分離)
- ステータス: 確定

---

## 1. 基本方針

一般ユーザー向けのプロダクトとして開発する(開発者本人や特定個人のための道具ではない)。想定する中心ユーザーは以下の一人に代表させる。

**「週の初めに1週間分の服を計画したい、服好きの通勤者」**

## 2. 人物像

| 属性 | 内容 |
| --- | --- |
| 年齢・立場 | 20代後半〜30代の社会人。服を定期的に買う可処分所得がある |
| 生活 | 毎日出社(電車通勤)。屋外にいる時間が長く、朝晩の気温差に直接さらされる |
| 服装への関心 | 高い(ファッションが好き)。何を着るかを自分で決めたい |
| 中心的な困りごと | **気温を読み違えて服装を失敗する**(寒すぎ・暑すぎ)。気温の数字と自分の服の対応が体感として掴めていない |
| 現状の代替手段 | 天気アプリで気温だけ見る。服との対応は毎回勘で、記録は残らない |
| 利用タイミング | **週の初めに1週間分をまとめて**計画・入力する |
| 使い続ける動機 | **着回しの最適化** — 同じ服ばかり着ていないかを把握し、手持ちを使い切りたい |
| 地域切替を使う場面 | **実家・二拠点の行き来**。定期的に別地域に滞在し、両方の気温を見比べる |
| 最大の離脱要因 | **入力が面倒なこと**。項目数・タップ数が多いと続かない |

## 3. この人物像から導かれる設計方針

- **1画面で1週間分を一括入力できること**が最優先。`/forecast` に予報表示とコーデ入力を統合し([specification.md §3](./specification.md))、`PUT /api/coordinates` を items 最大7件の一括 upsert とする設計([architecture.md §5](./architecture.md))は、この利用パターンに直接対応する
- **入力項目を増やさない**。アウター/トップス/ボトムスの3項目を維持し、メモ・小物の追加([specification.md §2.3](./specification.md) Could)は先回りして実装しない
- **地域切替は例外機能ではなく日常的に使われる**。二拠点利用を前提とするため、切替中に保存したコーデへ表示中地域の気温を記録する方針([architecture.md 決定事項 #29](./architecture.md))は必須要件として扱う
- **コーデ写真([specification.md §2.3](./specification.md) Should)は「あれば嬉しいが、なくても回る」**。テキスト記録だけで価値が成立するため、優先度は Should のまま据え置く。毎日撮影を要求する設計にはしない

## 4. 未解決の申し送り

継続動機である「着回しの最適化」は、現状の Must / Should 機能では直接満たされない。過去コーデ履歴([specification.md §2.3](./specification.md) Should)を実装する際に、**着用頻度・アイテムの偏りが見える形**にできないかを検討する(初回リリースのスコープは変えない)。

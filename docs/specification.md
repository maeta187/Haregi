## 1. アプリ概要

**Haregi(ハレギ)** は、旧称 FabuForecast のリビルドにあたり改名した。名前は「**晴れ**(天気)+**着**(服)」のダブルミーニングで、天気と服をつなぐというアプリの本質を表す。リポジトリ名・パッケージスコープは `haregi` を用いる(例: `@haregi/schema`)。

ユーザーは居住地域(気象庁の府県予報区)を登録してアカウントを作成し、その地域の週間気温予報(最高/最低気温)を確認しながら、日付ごとに「アウター・トップス・ボトムス」を記録する。**過去の記録を気温と紐付けて振り返れる**ことが、単なる天気アプリとの差別化ポイント。

> プロジェクト名の正式決定前に、ドメイン・ストア・商標(J-PlatPat)の被り確認を推奨。

### 1.1 ターゲットユーザー

想定する中心ユーザーは **「週の初めに1週間分の服を計画したい、服好きの通勤者」**(20代後半〜30代・毎日電車通勤・気温の読み違いによる服装の失敗が中心課題)。人物像の詳細と、そこから導かれる設計方針は [persona.md](./persona.md) を参照。機能の優先順位・UI の判断はこの人物を基準に下す。

### 2.2 天気予報

| 機能 | 優先度 | 備考 |
| --- | --- | --- |
| 登録地域の週間予報(最高/最低気温) | Must | 気象庁の予報データを利用(現行のハードコードを解消) |
| 地域マスタ(気象庁 府県予報区) | Must | 現行3件 → **全58区分**(北海道7・沖縄4・奄美含む)。検証済みマスタデータを生成済み([architecture.md §6](./architecture.md) 参照) |
| 表示地域の切替(一覧から選択) | Must | 予報画面のセレクタで任意の地域の予報を閲覧できる。登録地域はデフォルト表示地域として扱う。**切替中に保存したコーデには、その時点で表示していた地域の気温が記録される**(§2.3) |
| 予報取得失敗時の表示 | Must | 予報部にエラーメッセージ+再試行ボタン。**予報が取れなくてもコーデ入力・保存は継続できる** |

| 天気アイコン(晴れ/曇り/雨) | Should | 気象庁の天気コードをアイコンにマッピング |
| 降水確率 | Should | 同じレスポンスに含まれるため追加リクエスト不要 |

### 2.3 コーディネート(中核機能)

| 機能 | 優先度 | 備考 |
| --- | --- | --- |
| 日付ごとのコーデ登録(アウター/トップス/ボトムス) | Must | ユーザー×日付で一意(upsert)。**記録時点の予報気温スナップショットを自動保存**する(§2.5 の布石。ユーザー操作は不要)。基準は**画面で表示中の地域**の予報とし、画面に出ていた気温と記録が一致することを保証する。保証の方式は **`snapshotId` の往復**(画面が受け取った予報の世代 ID を保存時に送り返し、サーバーが同一世代のキャッシュから気温を引く)。予報が取れない場合は気温なしで保存([architecture.md 決定事項 #29 / #30](./architecture.md) 参照) |
| 保存済みコーデの表示・編集 | Must | 予報画面に既存データを反映。**編集時に既存の気温スナップショットを失わない**(`snapshotId` が送られない場合、保存済みの気温・地域・予報発表時刻はそのまま維持する。決定事項 #31) |
| 過去コーデの履歴一覧(最小版) | **Must** | **保存した記録を後から見る唯一の手段**であり、これがないと「気温と紐付けて振り返る」という本アプリの価値が初回リリースで成立しない。最小版のスコープは**日付・3項目・保存気温・地域名を直近30件、日付降順で一覧表示するだけ**。写真・集計・フィルタ・ページネーションは含めない |
| コーデの削除 | Should | 写真がある場合はストレージのオブジェクトも削除 |
| コーデ写真のアップロード(1日1枚) | Should | 5MB 程度・jpeg/png/webp に制限(サーバー側で強制できるかはストレージ契約先の presigned POST 対応に依存。[architecture.md §8](./architecture.md) 参照) |
| 履歴一覧の拡張(写真併記・期間フィルタ) | Should | 最小版の上に積む。当日の写真も併記(**サムネイルは生成せず原寸を縮小表示**。リサイズは Could) |
| 着用頻度・アイテムの偏りの可視化 | Should | ペルソナの継続動機である「着回しの最適化」に直接対応する([persona.md](./persona.md) §4)。履歴拡張と併せて検討する |
| 「似た気温の日に何を着たか」参照 | Could | 差別化機能。予報気温 ±2℃ の過去記録を提示 |
| AI コーディネート提案(写真 × トレンド × 天気) | Could(将来構想) | §2.5 参照 |
| メモ・小物など項目追加 | Could | |

### 2.5 将来構想: AI コーディネート提案(Could)

保存済みのコーデ写真・過去の着用記録・ファッショントレンド情報・週間予報を組み合わせ、「明日はこの服装がおすすめ」を生成する機能。初回リリースには含めないが、設計段階から布石を打っておく(技術的な前方互換の担保は [architecture.md §5](./architecture.md) 参照)。

**実現方式(想定)**

1. 対象日の予報(気温・天気)を取得
2. 似た気温(±2℃程度)の過去コーデ(写真 + テキスト)を抽出
3. トレンド情報を取得(下記課題参照)
4. 1〜3 をマルチモーダル LLM API(Claude API 等)に渡し、手持ちの服を踏まえた提案文を生成
5. 生成結果は日付×地域単位でキャッシュしコストを抑制

**課題・リスク(実装時に要調査)**

- **トレンド情報の入手経路が最大の課題**。公開のファッショントレンド API はほぼ存在しないため、候補は (a) Web 検索 API 経由でファッションメディアを要約 (b) 季節・気温帯ごとの静的なトレンド辞書を自前管理 (c) LLM の一般知識に季節情報を添えて委ねる、のいずれか。コストと鮮度のバランスで選定する
- **LLM API はスタック初の従量課金要素**。ユーザーあたりの生成回数制限とキャッシュを必須とする
- 気象庁の予報値は改変せずそのまま提案の入力に使う(独自の気象予測を生成しないため、気象業務法上の予報業務許可は不要のまま)

## 4. 入力バリデーション(現行仕様を踏襲)

| 項目 | ルール |
| --- | --- |
| ユーザー名(表示名) | 必須 / **1〜20文字 / 文字種の制限なし(日本語可)**。前後の空白は除去し、除去後に空なら不正。**一意制約は付けない**(ログイン ID はメールアドレス) |
| メールアドレス | 必須 / メール形式 |
| 登録地域 | 必須 / 地域マスタ(気象庁 府県予報区)に存在するコード |
| パスワード | 必須 / 8〜20文字 / 小文字英字と数字を含む |
| パスワード確認 | パスワードと一致 |
| コーデ各項目 | 任意 / 前後の空白を除去した上で最大50文字 |
| コーデの日付 | 必須 / JST の `YYYY-MM-DD` / **実在する暦日**(`2026-02-30` 等は不正)/ 保存可能範囲は**今日から前後1年以内** |
| コーデの一括保存(items) | 最大7件 / **リクエスト内で日付が重複していたら 400**(サーバー側で先勝ち等の暗黙処理をしない) |

**ユーザー名のルールを現行アプリから変更した理由**: 現行は「8文字以上・英数字のみ」だったが、これは日本語話者が本名やニックネームを使えず、会員登録時点での離脱要因になる。ペルソナの最大の離脱要因が「入力が面倒なこと」([persona.md](./persona.md))であること、ログイン ID がメールアドレスであり表示名に識別子としての役割がないことから、制限を外す。

**空のコーデの扱い**: 3項目(アウター/トップス/ボトムス)がすべて任意のため、空文字だけのレコードを作れてしまう。**前後の空白を除去した上で3項目すべてが空の場合、その日付は「保存しない」ではなく「既存レコードがあれば削除する」**として扱う(ユーザーから見れば「全部消したら記録が消える」という自然な挙動になる)。空レコードを DB に残さない。

- エラーメッセージは日本語(現行文言を流用)
- バリデーションはフロント(UX 用)とサーバー(防御用)の両方で行う。実装方式は、会員登録・アカウント設定・パスワード変更が [architecture.md §7](./architecture.md)(Better Auth の `hooks.before`)、コーデ各項目が [architecture.md §5](./architecture.md)(`@hono/zod-validator`)

## 5. 表示・挙動の仕様

- **日付表示**: `YYYY年M月D日`、気温は `℃` 表示(現行仕様を踏襲)
- **日付の基準**: すべて日本時間(JST)。深夜0時前後でも「今日」の判定がぶれないこと
- **障害時挙動**: 気象庁からの予報取得に失敗した場合、予報部にエラーメッセージと再試行ボタンを表示する(取得済みの古いデータがあればそれを表示)。コーデの入力・保存は予報なしでも継続できる
- **出典表記**: 「出典: 気象庁ホームページ」を予報表示部またはフッターに常時表示する
- **予報の鮮度と出どころの表示**: 予報表示部に**予報の発表時刻**と、古いデータを表示している場合はその旨(例:「◯時◯分時点の予報」)を出す。また気温は**地域の代表アメダス地点の予報**であり利用者の現在地の体感とは異なりうるため、地点名または「地域の代表地点の予報」であることを明示する。これがないと、地域の代表値であることに起因する差をアプリの不具合と受け取られる
- **同時編集の競合**: 同じ週を2つの画面(別タブ・スマホと PC 等)で編集した場合、古い画面からの一括保存で新しい変更が消えないこと。保存リクエストの各行に読み込み時の `updatedAt` を含め、サーバー側で不一致を検出したら **409 を返して再読み込みを促す**(上書きを黙って通さない。[architecture.md 決定事項 #32](./architecture.md) 参照)
- **未保存の変更**: 1画面で1週間分を編集する構造上、保存前に離脱すると入力が失われる。**未保存の変更がある状態での画面離脱時には警告する**

### 初回リリースの位置づけ(重要)

**初回リリースは限定公開(クローズドα版)とし、不特定多数への一般公開はしない。** 理由は、パスワードリセット・アカウント削除が未実装の段階では以下が成立しないため:

- メールアドレスの入力を誤っただけで復旧手段がなくなる
- パスワード忘失を DB の直接操作で救済する運用になり、危険かつ再現性がない
- ユーザーからのデータ削除要求に安全に応じられない

**一般公開のゲート**(すべて満たすまで公開しない):

1. パスワードリセットとアカウント削除の実装(§2.1)
2. [release-checklist.md](./release-checklist.md) のチェックリストを全項目クリア

なお「パスワード忘失時は DB を直接操作して対応する」という当初の割り切りは、限定公開の期間中に限って有効とする。

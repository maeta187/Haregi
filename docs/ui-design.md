# Haregi UI デザイン方針

Haregi の Must 画面を対象に、画面構造・視覚言語・コンポーネント・レスポンシブ・アクセシビリティの方針を定義する。

- 作成日: 2026-08-09
- ステータス: 提案
- 対象: `/`、`/signup`、`/login`、`/forecast`、`/history`
- 参照: [persona.md](./persona.md)、[specification.md](./specification.md)、[architecture.md](./architecture.md)、[implementation-plan.md](./implementation-plan.md)、[release-checklist.md](./release-checklist.md)
- 優先順位: 上記の規範文書と矛盾する場合は、規範文書を正とする

## 1. この文書のスコープ

この文書で決めるもの:

- Haregi の機能と UI 領域の対応
- 各画面の情報階層とレイアウト
- 配色・書体・余白・角丸の方針
- コンポーネントの責務と状態
- PC / タブレット / モバイルの再配置方針
- アクセシビリティ、文言、モーションの設計指針

この文書で行わないもの:

- `apps/web` のコード変更
- コンポーネントやスタイルの実装
- TDD、テストコードの追加、ブラウザ検証
- 第三者サイトの写真・ロゴ・コピー・正確な色値・レイアウト寸法の転用
- 第三者サイトから抽出した DNA の `design.md` 化

## 2. デザインの前提

### 2.1 中心ユーザー

「週の初めに1週間分の服を計画したい、服好きの通勤者」を中心に置く。

このユーザーにとって最も重要なのは、天気を詳しく分析することではない。7日分の気温と服装を短時間で対応付け、まとめて保存できることである。そのため、画面の華やかさよりも次を優先する。

1. 7日分を見渡せる
2. 気温と入力欄の対応を迷わない
3. 入力中の地域と保存される気温の関係が分かる
4. 予報が失敗しても作業を中断しない
5. 保存済み・未保存・競合の状態を見失わない

### 2.2 主行動

主行動は「表示中地域の週間予報を見ながら、最大7日分のコーデを一括保存する」。

`/forecast` はダッシュボードではなく、週次計画のための作業台として設計する。グラフや指標を増やさず、予報と3つの入力項目を同じ日付のまとまりとして扱う。

### 2.3 トーン

トーンは **soft utilitarian（柔らかい実用品）** とする。

- 実用品: 日付、気温、地域、入力状態を正確に読める
- 柔らかさ: 温かい紙面色、衣服を連想する落ち着いた質感、強すぎない角丸
- ファッション性: ランディングとワードマークだけに明確な書体差を持たせる
- 非対象: 子ども向けの丸さ、派手な多色使い、天気アプリらしい青一色、EC サイトの模倣

## 3. 参照サイトからの変換

第三者サイトから引き継ぐのは、固有表現ではなく構造上の考え方だけとする。

| 抽象 DNA | Haregi での解釈 | 引き継がないもの |
| --- | --- | --- |
| 複数の探索入口 | 予報、週次入力、履歴を役割別に明確化 | 商品カテゴリ、ブランド一覧、セール導線 |
| 三領域の非対称構図 | 予報情報、コーデ入力、保存状態の三領域 | 写真を使ったトリプティクの寸法 |
| 暖かい物質感 | 布・紙を思わせる温かいニュートラル | 元サイトの正確な背景色・革色 |
| 数字用の書体役割 | 日付・最高気温・最低気温を表組み数字で整列 | 元サイトが読み込む書体そのもの |
| 密度の高い商品カード | 1日単位の予報・入力行と履歴行 | 商品写真、価格、販売状態 |
| 複数の小さなモーション | 保存状態と表示切替に限定した知覚補助 | 自動スライダー、無限マーキー、画像拡大 |

全体の構造は、参照元の Ecosystem Index 型から **Workbench 型**へ変更する。Haregi の価値は閲覧の楽しさより、7日分を計画し終えられることにあるためである。

## 4. 全体の情報設計

### 4.1 ルートと主目的

| 画面 | 主目的 | 主操作 | 副操作 |
| --- | --- | --- | --- |
| `/` | Haregi の用途を理解する | アカウントを作る | ログインする |
| `/signup` | 利用を開始する | アカウントを作る | ログインへ移動 |
| `/login` | 既存アカウントで入る | ログインする | 会員登録へ移動 |
| `/forecast` | 1週間分を計画する | 1週間を保存 | 地域切替、予報再取得 |
| `/history` | 気温と服装を振り返る | 直近30件を読む | 予報画面へ戻る |
| `/settings` | 登録情報を変更する | 変更を保存 | Should 実装時に設計を確定 |

### 4.2 ナビゲーション

未ログイン時とログイン時で、目的の異なるナビを分ける。

未ログイン時:

- 左: Haregi ワードマーク
- 右: `ログイン` と主 CTA `アカウントを作る`
- 中央をリンクで埋めない。ページ内アンカーは置かない

ログイン時:

- 左: Haregi ワードマーク
- 中央: `1週間の計画`、`履歴`
- 右: ユーザー名を起点にしたメニューとログアウト
- `/settings` 実装後はユーザーメニュー内へ追加する
- モバイルは shadcn/ui の Sheet にまとめる

リンク名は機能名より利用目的を優先する。`予報` だけではコーデ入力を含むことが伝わらないため、ナビでは `1週間の計画` と表現する。

### 4.3 フッター

ランディングのみ、単一行の小さなフッターを置く。

- Haregi
- 出典・利用条件に関する短い表記
- 必要になった時点で規約・プライバシーポリシーへのリンク

アプリ内画面はフッターを主な操作領域にしない。気象庁の出典は `/forecast` の予報領域に常時表示し、ページ最下部まで移動しないと見えない配置を避ける。

## 5. `/forecast` — 週間予報とコーデ入力

### 5.1 画面の構造

デスクトップでは、参照 DNA の三領域構成を機能に置き換える。

```text
┌─────────────────────────────────────────────────────────────────┐
│ Haregi      1週間の計画  履歴                         ユーザー   │
├──────────────┬──────────────────────────────────────┬───────────┤
│ 地域・予報情報 │ 7日分のコーデ入力                      │ 保存状態  │
│              │                                      │           │
│ 東京都        │ 8月10日  晴  34 / 26℃                 │ 変更 3日  │
│ 地域を切替    │ アウター ｜トップス ｜ボトムス          │           │
│              │──────────────────────────────────────│ 1週間を   │
│ 代表地点      │ 8月11日  曇  31 / 25℃                 │ 保存      │
│ 東京          │ アウター ｜トップス ｜ボトムス          │           │
│              │──────────────────────────────────────│ 保存済み  │
│ 11:00発表     │ … 7日分                              │ 14:32     │
│ 気象庁出典    │                                      │           │
└──────────────┴──────────────────────────────────────┴───────────┘
```

三領域の役割:

1. **予報コンテキスト**: 表示地域、代表地点、発表時刻、鮮度、出典
2. **週間プランナー**: 日付、天気、最高・最低気温、3入力項目
3. **保存コンテキスト**: 変更件数、保存中、保存済み、失敗、競合

視線と入力の往復を減らすため、日付・天気・気温は各入力行の先頭にも表示する。左領域は予報全体の出どころ、行頭はその日に着る服を判断する情報という役割に分ける。

### 5.2 週間プランナー

7日を同じ構造の行として並べる。ただし、カードを7枚並べるのではなく、軽い罫線で連続した作業表として見せる。

各行の順序:

1. 表示日付（`YYYY年M月D日`）と曜日
2. 天気、最高気温、最低気温
3. アウター
4. トップス
5. ボトムス
6. その日の入力状態

入力項目の仕様:

- ラベルを常時表示し、placeholder をラベル代わりにしない
- placeholder は入力例だけに使う。例: `薄手のトレンチコート`
- 50文字制限は通常時に強調せず、上限へ近づいたときだけ残数を示す
- 3項目がすべて空の既存行は、保存時に削除されることを行内で知らせる
- 予報値はフォーム値に含めず、表示専用とする
- `snapshotId` は利用者に見せず、表示中の予報世代を保存時に往復させる
- 各行の `updatedAt` も表示せず、競合検出のために保持する

### 5.3 地域切替

地域切替は設定変更ではなく、その週を考える場所の切替として扱う。

- トリガーには現在の地域名を表示する
- 58区分は地域グループごとに分け、キーボード検索できる選択 UI とする
- 登録地域には `登録地域` のテキストラベルを付ける
- 選択 UI 内に「ここで切り替えても登録地域は変わりません」と明記する
- 切替後は予報と `snapshotId` をまとめて更新する
- 未保存の入力がある場合、地域切替で入力を破棄しない。保存される気温の地域が変わるため、切替後の状態を明確に表示する

### 5.4 予報の鮮度と障害

予報コンテキストには次を常時表示する。

- 地域名
- 代表アメダス地点名、または「地域の代表地点」
- 予報発表時刻
- 取得状態: `最新` または `以前に取得した予報`
- `出典: 気象庁ホームページ`

stale データ:

- 気温と天気はそのまま表示する
- 注意アイコンと `11:00時点の予報を表示しています` を併記する
- stale であることを色だけで伝えない

予報を取得できない場合:

- 予報領域だけをエラー状態にする
- 文言: `予報を取得できませんでした。コーデは入力・保存できます。`
- 操作: `予報を再取得`
- 入力欄と保存操作を disabled にしない
- 気温がない日は `—℃` ではなく `気温記録なし` と表示し、値の欠損を明示する

### 5.5 保存状態

保存成功を毎回トーストで祝わない。結果が画面上で分かるため、成功は保存領域の表示更新で伝える。トーストは失敗・競合・画面外で起きた重要な結果に限定する。

| 状態 | 表示 | 操作 |
| --- | --- | --- |
| 変更なし | `保存済み` | 保存ボタンは disabled |
| 変更あり | `3日分を変更中` | `1週間を保存` |
| 保存中 | `保存しています` | ラベルを保った loading 状態 |
| 成功 | `保存済み 14:32` | 追加通知なし |
| 通信失敗 | `保存できませんでした。入力内容は残っています。` | `もう一度保存` |
| 409競合 | `別の画面で更新されています。最新の内容を読み込んでください。` | `最新の内容を読み込む` |

競合時は自動再読込しない。入力中の内容が失われるため、利用者が再読込を選ぶまで保持する。

### 5.6 未保存離脱

未保存の変更がある状態で別ルート・戻る・タブ終了を試みた場合は警告する。

- 見出し: `変更が保存されていません`
- 本文: `この画面を離れると、入力した1週間分の変更が失われます。`
- 主操作: `入力を続ける`
- 副操作: `保存せず離れる`

主操作は安全な選択を優先する。確認ダイアログを汎用の `OK / キャンセル` にしない。

## 6. モバイルの週間プランナー

モバイルでは、デスクトップの表を横スクロールさせない。DOM 上の日付順を保ったまま、1日を1つの縦ブロックへ変換する。

```text
┌──────────────────────────┐
│ Haregi        メニュー   │
├──────────────────────────┤
│ 東京都  ▼                │
│ 東京・11:00発表・最新     │
│ 出典: 気象庁ホームページ  │
├──────────────────────────┤
│ 8月10日（月） 晴          │
│ 最高 34℃    最低 26℃     │
│ アウター [              ] │
│ トップス [              ] │
│ ボトムス [              ] │
├──────────────────────────┤
│ 8月11日（火） 曇          │
│ …                        │
├──────────────────────────┤
│ 3日分を変更中  1週間を保存 │  ← sticky
└──────────────────────────┘
```

方針:

- 320 / 375 / 414 px で横スクロールを発生させない
- 日付ブロックは初期状態ですべて展開し、開閉のための余計なタップを増やさない
- 入力順は日付内でアウター → トップス → ボトムス
- sticky 保存バーは safe area を考慮する
- 入力中にソフトウェアキーボードが開いても、現在の入力欄と保存バーが重ならない
- タップ領域は44×44 CSS px以上、粗いポインターでは48pxを目標にする
- 768px前後では2日を並べず、読みやすい単一列を維持する。横幅より入力の連続性を優先する

## 7. `/history` — 過去コーデ履歴

履歴は最小版の要件を越えて分析画面にしない。直近30件を、日付降順の読みやすいインデックスとして見せる。

各行の情報順序:

1. 日付
2. 保存時の最高・最低気温
3. 保存時の地域名
4. アウター
5. トップス
6. ボトムス

デスクトップは日付・気温・地域を左、3項目を右に置く。モバイルは日付と気温を先頭にした縦一列へ変える。写真・フィルタ・ページネーション・着用頻度グラフは Should 以降まで置かない。

気温がない記録は `気温記録なし` と表示する。地域名がない古い記録を将来扱う場合も、空欄ではなく `地域記録なし` とする。

空状態:

- 見出し: `保存したコーデはまだありません`
- 説明: `1週間の計画を保存すると、気温と一緒にここへ残ります。`
- 操作: `1週間を計画する`

## 8. ランディングページ

ランディングは機能カードを3枚並べる構成にしない。実際の利用手順を見せる Workbench 型とする。

### 8.1 ヒーロー

H2 Split Diptych を基礎にする。

- 左: 短い主張、説明、CTA
- 右: Haregi の週間プランナーを示す実画面または忠実なデータ模型
- 比率: 7 / 5
- 区切り: 罫線より余白を優先
- 写真を必須にしない
- ブラウザのURLバーやウィンドウボタンを描いた偽のブラウザ枠は作らない

コピー案:

- 見出し: `天気を見て、1週間の服を決める。`
- 説明: `最高・最低気温を見ながら、アウター、トップス、ボトムスを7日分まとめて記録できます。`
- 主 CTA: `アカウントを作る`
- 副リンク: `ログインする`

### 8.2 セクション順

1. ヒーローと週間プランナーのプレビュー
2. 予報と3項目を同じ日付で見比べられること
3. 表示中地域の気温が記録に残ること
4. 過去の服装を気温と一緒に振り返れること
5. 単一 CTA `アカウントを作る`

架空の利用者数、改善率、証言、ブランドロゴは置かない。実在する根拠が得られるまでは、機能そのものを証拠として見せる。

## 9. 認証画面

`/signup` と `/login` は共通の画面骨格を使い、フォームの項目だけを変える。

デスクトップ:

- 左 5/12: Haregi の短い説明とワードマーク
- 右 7/12: フォーム
- 外側の巨大カードにフォームカードを入れる二重構造を避ける

モバイル:

- ワードマーク
- 見出し
- フォーム
- 画面切替リンク

フォーム方針:

- ラベルは入力欄の上に常時表示
- バリデーションは初回 blur 後に表示し、その後は入力に追従
- helper と error は同じ1行分の領域を使い、表示時のレイアウト移動を防ぐ
- パスワード条件は入力前から読める位置に表示する
- signup の地域は登録地域であることを明記し、`/forecast` の一時的な地域切替と区別する
- ボタン文言は `アカウントを作る`、`ログインする` とし、`送信` や `OK` を使わない

## 10. 視覚システム

参照元のトークンは使用せず、Haregi 固有の値として再構成する。以下は実装前の候補であり、実装時に APCA または WCAG AA の基準でコントラストを検証して確定する。

### 10.1 色

| トークン案 | 値 | 用途 |
| --- | --- | --- |
| `paper` | `oklch(97% 0.014 90)` | 基本背景。温かい生成り |
| `paper-2` | `oklch(94% 0.018 90)` | 行の区切り、hover 背景 |
| `surface` | `oklch(90% 0.022 90)` | 選択済み・固定領域 |
| `ink` | `oklch(24% 0.025 175)` | 本文、主要ラベル |
| `muted` | `oklch(43% 0.020 170)` | 補足、発表時刻 |
| `rule` | `oklch(82% 0.018 90)` | 罫線、入力境界 |
| `accent` | `oklch(52% 0.140 242)` | リンク、選択、focus。空色 |
| `accent-ink` | `oklch(97% 0.014 90)` | accent 面上の文字 |
| `temperature-high` | `oklch(56% 0.150 40)` | 最高気温。文字と記号を併用 |
| `temperature-low` | `oklch(50% 0.110 242)` | 最低気温。文字と記号を併用 |
| `success` | `oklch(50% 0.110 145)` | 保存済み |
| `warning` | `oklch(54% 0.130 75)` | stale、未保存 |
| `error` | `oklch(54% 0.180 25)` | 入力・保存エラー |

規則:

- 基本は paper / ink / rule で構成する
- accent の面積は各 viewport の約3%以内を目安にする
- 主ボタンを accent で大きく塗る場合は `accent-ink` のコントラストを必ず確認する
- 高温・低温・成功・警告・エラーを色だけで区別しない。必ずラベルまたはアイコンを併用する
- ダークモードは Could のため、初回設計に混ぜない

候補色は paper 上の本文用途と accent 面上の文字について WCAG のコントラスト比を事前確認済みで、いずれも 4.5:1 以上になる組み合わせにしている。ただし、実装時は実際の font-weight、文字サイズ、重なり先を含む computed color で再確認する。

### 10.2 書体

2ファミリーまでとする。

- UI・本文・数字: **IBM Plex Sans JP**
- ワードマークとランディングの主見出し: **Shippori Mincho** の太字・ローマン体

アプリ内の見出しは IBM Plex Sans JP の太字を使い、明朝体を多用しない。Shippori Mincho はワードマークとランディングの主見出しという2つの役割だけに限定する。

数字を含む領域では `tabular-nums` を使う。特に日付、最高・最低気温、発表時刻、保存時刻の桁を揃える。

文字サイズの基準:

- 本文・入力値: 16px以上
- 補助文: 14px以上
- 入力ラベル: 14–16px
- アプリ画面見出し: 25–31px程度
- ランディング見出し: 44–72pxの範囲で `clamp()`
- 行間: 本文 1.55、見出し 1.1–1.25

### 10.3 余白・角丸・境界

4px基準の余白スケールを使う。

| 名前 | 値 |
| --- | --- |
| `2xs` | 4px |

## 11. コンポーネント構成案

実装時の機能優先スライスに合わせ、UI責務を次のように分ける。ここではファイルを作成せず、所有関係だけを定義する。

### 11.1 共通シェル

- `AppHeader`: 認証状態と現在ルートを props で受け取る
- `MobileNavigation`: Sheet 内のルートリンク
- `InlineFooter`: ランディング用の単一行フッター
- `UnsavedChangesDialog`: 画面離脱の判断だけを返す

### 11.2 forecast feature

- `RegionSwitcher`: 表示地域の選択
- `ForecastContext`: 地域、代表地点、発表時刻、鮮度、出典
- `ForecastDaySummary`: 日付、天気、最高・最低気温
- `ForecastError`: 再取得と入力継続の説明

### 11.3 coordinate feature

- `WeekPlanner`: 最大7日の入力行を束ねる純粋コンポーネント
- `CoordinateDayFields`: 1日分の3入力項目
- `SaveStatus`: dirty / saving / saved / error / conflict の表示
- `StickySaveBar`: モバイルで保存操作を常時到達可能にする
- `CoordinateHistoryList`: 直近30件の履歴
- `CoordinateHistoryItem`: 日付・気温・地域・3項目の表示

### 11.4 auth feature

- `SignupForm`
- `LoginForm`
- `AuthPageIntro`

`/forecast` のルートは forecast と coordinate を合成する。forecast から coordinate を直接参照させず、必要な `snapshotId` と表示情報はルートまたは許可された `coordinate → forecast` の依存方向で渡す。

## 12. インタラクションと状態

### 12.1 8状態

ボタン、入力、選択 UI は次の状態を設計対象とする。

1. default
2. hover
3. focus-visible
4. active
5. disabled
6. loading
7. error
8. success

入力欄は全状態で1pxの境界幅を維持し、focus は2pxの outline で示す。error は色に加えてメッセージとアイコン、`aria-invalid` を使う。disabled は opacity だけに頼らず、カーソル、属性、説明を併用する。

### 12.2 通知の使い分け

- 保存成功: 画面内の `保存済み` へ更新。トーストなし
- 保存失敗: エラートーストと再試行
- 409競合: 画面内バナーまたは持続するトーストで再読込を要求
- 予報取得失敗: 予報領域内に表示。グローバルトーストだけで済ませない
- バリデーション: 各入力欄の直下

### 12.3 ローディング

- 予報・履歴: 最終形が予測できるため skeleton
- 保存: ボタン内 loading。入力内容は消さない
- 150ms未満で終わる処理は spinner を表示しない
- 長い待機に見せかける演出は行わない

## 13. モーション

Workbench 型として、モーションは次の3種類までに限定する。

1. ボタンの active: 1px沈む、100–150ms
2. 地域選択・Sheet・Dialog: opacity と transform、200–300ms
3. 保存状態の切替: opacity crossfade、150–200ms

禁止:

- 日付行すべてのスクロール連動 reveal
- 天気アイコンの常時ループ
- 自動カルーセル
- 背景の無限マーキー
- `transition: all`
- 複数要素への一律 hover scale
- width / height / margin / padding のアニメーション

`prefers-reduced-motion: reduce` では空間移動をやめ、150ms以下の opacity 変化か即時切替にする。focus ring は常に即時表示し、アニメーションさせない。

## 14. レスポンシブ方針

モバイルを基本とし、内容が崩れる位置でレイアウトを拡張する。

- 320 / 375 / 414px: 1日1ブロック、sticky 保存バー、Sheet ナビ
- 640px前後: 余白を拡張するが、週間入力は単一列を維持
- 960px前後: 予報コンテキスト / プランナー / 保存状態の三領域へ切替
- 1440px以上: 入力欄の横幅を広げ、外側の余白を増やす。情報密度は増やさない

共通規則:

- 横スクロールさせない
- primary CTA、ナビリンク、タブ、保存ボタンの文言を改行させない
- `100vw` を前提にしない
- sticky UI はモバイルの safe area とソフトウェアキーボードを考慮する
- hover にしか存在しない操作を作らない
- 日付行の読み上げ順は画面幅で変えない

## 15. アクセシビリティ

- 日本語本文は16px以上を基本とする
- 通常本文はWCAG 4.5:1以上、大きな文字・アイコン・UI境界は3:1以上を最低条件とする
- focus-visible は2–3px、背景と要素の両方に対して3:1以上
- 全操作をキーボードで実行できる
- タッチ領域は44×44 CSS px以上
- 天気、温度、保存状態、エラーを色だけで伝えない
- 7日分の入力は日ごとに `fieldset` / `legend` 相当のまとまりを持たせる
- 保存・再取得・競合などの非同期結果は適切な `aria-live="polite"` で知らせる
- stale 予報は発表時刻を読み上げ可能なテキストとして含める
- placeholder をラベル代わりにしない
- エラーメッセージを対応する入力と `aria-describedby` で関連付ける
- モーダル・Sheet はフォーカスを閉じ込め、Escape と明示ボタンで閉じられるようにする

## 16. 文言方針

Haregi の文言は、服装を指示するのではなく、利用者が自分で決めるための材料を整理する。

- 具体的な動詞を使う: `1週間を保存`、`予報を再取得`、`最新の内容を読み込む`
- `送信`、`OK`、`こちらをクリック`を使わない
- エラーは、起きたこと → 影響 → 次の操作の順で書く
- 入力ミスを冗談や感嘆符で扱わない
- 気象庁の予報値を独自評価する表現を加えない
- 「この気温ならこの服が正解」のように、仕様外の服装提案を行わない
